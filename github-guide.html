TYPE TOWER
GitHub超入門

GitHubを知らない人向けに、「GitHubとは何か」から、コードの書き方、保存、3人で同時に作業する流れまでをまとめています。

ここから始める 制作ロードマップへ
START

最初に3人でやること

コードを書く前に、ここだけ終わらせます。

  1. GitHubアカウントを作る

    3人ともGitHubへ登録してログインします。すでにアカウントがある人はそのままでOKです。

  2. 2人のGitHubユーザー名をリポジトリ所有者へ送る

    ユーザー名はプロフィールに表示される名前です。メールアドレスではなくGitHubのユーザー名を共有します。

  3. 2人をCollaboratorへ追加する

    所有者が type-tower → Settings → Collaborators → Add people から2人を招待します。招待された2人はメールまたはGitHub上で招待を承認します。

  4. 3人ともtype-towerを開けるか確認する

    ファイル一覧が見えて、ブランチを作れる状態なら準備完了です。

このチームの基本ルール

main は完成版を置く場所です。3人が同時に作業するときは、原則として mainを直接書き換えず、自分の作業用Branchを作ってから編集します。

BASIC WORDS

まずこの6個だけ覚える

GitHubの用語を全部覚える必要はありません。

Repository

プロジェクトの共有フォルダ。
今回なら type-tower 全体のこと。

main

完成版・基準版。
基本的に動く状態を置いておくBranch。

Branch

作業用のコピー。
mainを壊さずに各自がコードを書ける場所。

Commit

変更のセーブ。
「ここまで変更した」という記録をGitHubへ残す。

Pull Request

mainへ入れていい？という申請。
変更内容を確認してから統合するために使う。

Merge

Branchの変更をmainへ合体すること。
Pull Requestを確認して問題なければMergeする。

main→Branchを作る→コードを書く→Commit→Pull Request→Merge
BEFORE CODING

コードを書く前にBranchを作る

1人1個ではなく、1つの作業につき1Branchにします。

  1. type-towerのトップを開く

    ファイル一覧が見える画面へ戻ります。

  2. Branch欄の「main」を押す

    ファイル一覧の上や左側にあるBranch選択を開きます。

  3. 新しいBranch名を入力する

    例：feature/step1-screen、feature/step2-kanji、fix/result-bug

  4. Create branchを押す

    作成元は基本 main にします。

  5. 画面に新しいBranch名が表示されているか確認する

    main のままなら編集を始めないでください。

Branch名のおすすめ

feature/step1-screen のように、何の作業か分かる名前にします。「test」「aaa」「new」だけの名前は避けます。

METHOD 1

GitHubの画面で直接コードを書く

1ファイルだけの小さい修正に向いています。

使う場面：文章修正、JSONの問題追加、CSSの数行修正、README修正など。
  1. 先に自分のBranchへ切り替える

    上に表示されているBranch名が main ではないことを確認します。

  2. 変更したいファイルを開く

    例：index.html、styles.css、data/kanji.json

  3. 右上の鉛筆マークを押す

    GitHubのファイルエディターが開きます。

  4. コードを書き換える

    変更した場所をもう一度見て、消してはいけないコードを消していないか確認します。

  5. Commit changesを押す

    Commit messageには変更内容を書きます。例：Add 10 easy kanji questions

  6. 自分のBranchへCommitする

    mainへ直接入れず、今作業しているBranchへ保存します。

  7. 作業が終わったらPull Requestを作る

    後述の「3人開発の流れ」に進みます。

新しいファイルを作りたいとき

リポジトリのファイル一覧で Add file → Create new file を使います。ファイル名を入力して内容を書き、最後にCommitします。

METHOD 2

github.devでVS Codeみたいに書く

HTML・CSS・JavaScriptを複数ファイル触る普段の作業はこちらがおすすめです。

使う場面：画面制作、ゲーム処理、複数ファイルの修正、新しい機能の追加。
  1. 先に自分のBranchへ切り替える

    GitHubの通常画面で作業用Branchを作って、そのBranchを表示しておきます。

  2. キーボードの「.」を押す

    github.devが同じタブで開きます。開かない場合はURLの github.com を github.dev に変えて開けます。

  3. 左のExplorerからファイルを開く

    VS Codeとほぼ同じ感覚で、HTML / CSS / JavaScript / JSONを複数開いて編集できます。

  4. 必要なら新しいファイル・フォルダを作る

    Explorerの新規ファイル・新規フォルダのボタンを使います。

  5. こまめに保存する

    編集途中の内容はブラウザ側に残りますが、GitHubへ確実に残すにはCommitが必要です。

  6. 左のSource Controlを開く

    枝分かれしたようなアイコンを押します。変更したファイル一覧が表示されます。

  7. 変更をStageする

    変更ファイル横の ＋、またはChanges横の ＋ を押します。

  8. Commit messageを書く

    例：Add typing answer validation

  9. Commit & Pushを押す

    変更が自分のBranchへGitHub上で保存されます。

  10. Pull Requestを作る

    Source Control上部のPull Requestアイコンから作るか、GitHubの通常画面へ戻って作ります。

github.devでできないこと

github.devには通常のターミナルや実行用PC環境がありません。コードを書く・検索する・Commitする用途が中心です。今回のHTML/CSS/JS制作ではかなり使えますが、最終的な動作確認はブラウザで行います。

TEAM WORK

3人で作るときは毎回この流れ

迷ったら、この8個を上から順番にやります。

  1. 1
    制作ロードマップで今のSTEPを確認

    3人で「今回どこまで作るか」を合わせる。

  2. 2
    mainから作業用Branchを作る

    1つの作業につき1Branch。

  3. 3
    GitHub編集 または github.devでコードを書く

    1ファイルの軽い修正はGitHub、通常の開発はgithub.dev。

  4. 4
    Commitする

    「何を変えたか」が分かるメッセージを付ける。

  5. 5
    Pull Requestを作る

    baseは main、compareは自分のBranchになっているか確認。

  6. 6
    別の1人が変更内容を見る

    Files changedを見て、関係ないコードを大量に消していないか確認。

  7. 7
    問題なければMerge

    Merge pull request → Confirm merge。終わったBranchは削除してOK。

  8. 8
    mainで動作確認して次のSTEPへ

    ブラウザで確認して、壊れていたら次へ進まない。

やる

  • 作業前にBranch名を確認
  • 小さめにCommitする
  • Pull Requestで変更を見る
  • 同じファイルを触るなら先に共有
  • Merge後にブラウザで確認

やらない

  • 3人でmainを直接編集し続ける
  • 他人のBranchを勝手に書き換える
  • 分からない競合を適当に消して直す
  • 大量変更を説明なしでMergeする
  • 動作確認せず次のSTEPへ進む
PULL REQUEST

Pull Requestの作り方

Branchで作った変更をmainへ入れる前の確認画面です。

  1. Commit & Pushまで終わらせる

    変更がGitHub上のBranchにある状態にします。

  2. GitHubのtype-towerを開く

    上部の Pull requests を開きます。

  3. New pull requestを押す

    またはBranchをPushした直後に表示される Compare & pull request を使います。

  4. Branchを確認する

    base: main ← compare: 自分のBranch になっていることを確認します。

  5. タイトルを書く

    例：STEP 3: タイピング判定を追加

  6. Create pull requestを押す

    これで他の2人が変更を見られます。

  7. Files changedを確認する

    意図したファイルだけ変わっているかチェックします。

  8. 問題なければMergeする

    Merge pull request → Confirm merge。

TROUBLE

困ったとき

「Conflict」と出た

同じ場所を別々に編集した可能性があります。分からないまま片方を消さず、どちらの変更を残すか3人で確認してから直します。

間違えてmainを編集した

慌てて消さず、まず何をCommitしたか確認します。まだCommit前なら編集を戻し、必要なら新しいBranchへ移してから作業します。

github.devで変更が消えそう

Source ControlからこまめにCommit & Pushします。Commitされていない変更はブラウザ側の状態に依存するため、大きな作業を長時間未Commitのままにしません。

他の人の変更が自分の画面にない

自分が古いBranchを見ている可能性があります。Merge済みの最新mainを基準に、新しい作業Branchを作って次の作業を始めます。
